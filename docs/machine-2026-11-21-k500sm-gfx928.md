# 新机实测记录：K500SM_AI / gfx928（2026-11-21）

平台标签是「异构加速卡AI 显存64GB PCIE」（021 组 / 华东一区昆山），**不是**之前那台「异构加速卡 BW」。
两者架构不同，本文件记录实测事实、因此失效的东西、以及要补的东西。

## 2. 因此失效、需要重建的东西

| 资产 | 状态 | 原因 |
|---|---|---|
| `benchmark/private/*/baseline.json`（66 份） | **全部失效** | 存的是旧机的 `environment: {device: BW, gcn_arch: gfx936…}`；基线是"同机分母"，跨架构不可比（铁律 4） |
| 现有评测数字（Correct / 真解 / speedup） | **不可与本机拼接** | 一是换机换架构，二是 1116 已把在线契约改成"原生 dtype + 任务容差" |
| wiki 硬件页 `wiki/hardware/gfx936.md` | **不描述这张卡** | 那 8 个实测值（80 CU / 68.7 GB / 1343.8 GB/s / 298/324/54 TFLOPS …）都来自 BW |
| 题面的硬件句 | **与实际不符** | 66 道题的 HIP/Triton 题面写 `Hygon DCU (gfx936)`；`environment.yaml` 的 `target_arch` 也是 gfx936 |
| `patches/kernelweaver-dcu-wiki` 的语料 | **arch 门槛不匹配** | 语料每个页 `architectures: [gfx936]`，`dcu_*.yaml` 里 `operator_memory_target_arch: gfx936`；用 gfx928 检索会被拒（`PublicKernelWiki(target_arch=…)` 校验） |
| aiter 适配器的 arch 映射 | 未验证 | 旧机 `gfx936 → BW200` 的 tuner 映射；gfx928 未必对得上，采基线前要确认 |
| 8.4 MB L2 → 实际 8192 KiB | 巧合一致 | 旧机记录的 8.4 MB 与这里的 8 MiB 接近，但不要据此推断其他参数 |

**保持有效的**：静态 shared 64 KiB 上限、wavefront 64、`#include <hip/hip_runtime.h>`、CUDA runtime 头/`CUDART_*`/PTX 不可用等"平台约束"仍然成立（DTK 26.04 + gfx928 实测确认了 SMEM 与 wavefront）。

## 3. 要补的东西（按顺序）

1. **Triton（DAS wheel）**：本机无外网，必须上传
   `triton-3.3.0+das.opt1.dtk2604.torch290-...cp311....whl`（旧机用过的那只），
   装完 `python3 -c "import triton; print(triton.__version__)"` 应回 `3.3.0+das.opt1.dtk2604`。
   装完必须跑一次 JIT 冒烟（vecadd + `tl.dot`），**gfx928 是否被这只 Triton 后端支持，目前未验证**。
2. **aiter（或其最小导入垫片）**：采 aiter 基线需要；旧机用的是 `aiter_shim`（60 个纯 Python 模块 + 309 个 tuner config）。
3. **决策：题面架构口径**
   - 方案 A（保留 benchmark 语义）：找平台要一张 **BW / gfx936** 的机器（旧 113 组那类），一切照旧，只重采基线。
   - 方案 B（迁移到 gfx928）：需要改 66 道题的题面硬件句、`environment.yaml` 的 `target_arch`、
     kernelbench 镜像、wiki 语料全部页面的 `architectures:` 与 `operator_memory_target_arch`、硬件页正文，
     并重采基线。工作量大，且会让"gfx936 时代"的历史数字彻底不可比。
   - 方案 C（双架构）：为 gfx928 单独一份 corpus/config 与基线目录，两套并存。
4. 决策落地后再谈重跑：重跑前先确认 1116 契约补丁已应用（`DCUKB_ROOT`），否则两个口径混在一张表里。

### 5.1 机器侧端到端验证（2026-11-21，真机）

把仓库打到 `/root/dcukb`，用 r3 证据里的历史候选做终审自检（`--skip-perf`，只看编译与隐藏 case）：

| 轨 | 任务 | 候选 | 结果 |
|---|---|---|---|
| Triton | `1002_paged_attention` | `final2/triton/…/best_code.py` | 静态审计通过 → **隐藏 case 7/7 通过** |
| HIP | `1015_lean_atten` | `final2/hip/…/best_code.py` | 静态审计通过 → `load_inline` 在 gfx928 上编译成功 → **隐藏 case 6/6 通过** |

顺带确认两条既有规则在新机上照常生效：

- `2001_activation` 的历史 HIP 候选被静态审计判负（`nn.functional.silu` / `nn.functional.gelu`）——
  即 1116 那版"解析 import 别名"的修复有效，`F.*` 写法不再绕过。
- 把 `reference.py` 直接当提交跑，会被判 `torch.einsum` / `torch.softmax` 违规，符合预期。

结论：**gfx928 上 HIP 与 Triton 两条轨都能编译、能跑隐藏 case**，题包与私有资产不需要改；
剩下的是基线、aiter 与 LLM 出口。
