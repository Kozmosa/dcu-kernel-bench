HIP device code includes hip/hip_runtime.h. The figures below were measured on the deployment described above; treat them as advisory budgets rather than vendor specifications, and re-query device attributes when the stack changes.

- Wavefront is 64 lanes (torch reports warp_size=64). A 32-lane assumption idles half the wave; size cooperation and reductions in multiples of 64.
- Static shared memory per block is 65536 B. Requesting 98304 B fails at compile time with OutOfResources: Hardware limit 65536. Keep tiles inside 64 KiB or split the reduction across blocks.
- Device attributes also report 2560 threads per workgroup, 196608 registers per compute unit, and 8.4 MB L2. Use them to bound launch geometry instead of reusing SM86 tables.
- Measured throughput available for sizing: 1343.8 GB/s device copy; matmul 298.34 fp16, 323.75 bf16, 54.26 fp32 TFLOP/s on 4096-cube operands.
- Compile surface actually available: hipcc accepts warpSize and __launch_bounds__, and provides warp-shuffle intrinsics; it does not provide CUDA runtime headers, cudaMalloc-type calls or the CUDART_* math constants, and PTX inline assembly is unusable. Write kernels against the hip API and use INFINITY where CUDA used a CUDART constant.
- On the Triton stack, triton.language.extra.libdevice resolves while tl.extra.cuda is the NVIDIA namespace; nested jit inlining, captured closures and tl.matrix_load have failed to compile here.

Shared storage and block barriers remain block-scoped. No performance guarantee follows from these numbers: they bound resources, not outcomes. Not measured here: LDS bank count, per-thread register limit, MFMA instruction shapes and asynchronous-copy availability. Read those from the installed compiler and device instead of assuming SM86 or AMD vendor values.
